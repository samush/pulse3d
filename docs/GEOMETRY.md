# Формат данных сцены (`plan.js`)

Вся геометрия квартиры — объект `const PLAN` в `plan.js`. Координаты в метрах,
в плане: `x` — вправо, `z` — «вниз» по плану БТИ, `y` — высота (потолок `H=2.7`
задан в `app.js`). Все стены осепараллельны.

## Высоты

- `y=0` — **чистовой пол**. От него заданы все высоты: мебель (основание 0 стоит на полу,
  столешница `0.91` — 91 см над полом), дверные проёмы (`2.1`), окна (`y0`/`y1` в `windows`),
  потолок (`H=2.7`), рост человечка (глаза `1.57`), плинтус (`0–0.1`), обои (от `0.1`),
  H-адреса сетки (`H10` = 1.0 м над чистовым полом).
- Слои пола лежат на миллиметры выше нуля, чтобы не мерцать: черновой `0.001`, клетки `0.003`, отделка
  `FLOOR=0.006`, адресная сетка `0.009`. Основание под квартирой — от `-0.12` до `0`.
- Пояса стен `slabs[].y0/y1` тоже считаются от чистового пола: `0–0.55` подоконная часть,
  `2.1–2.3` перемычка над дверями, `2.3–2.7` верх.
- Черновой пол/стяжка отдельно не моделируются — их толщина в сцене не нужна.

## Версия, единицы и начало координат

- `meta.version` — версия схемы плана (сейчас 2: добавлены `meta`, `doors`, `openings`, `baths`).
  Файлы разметки и задания агенту ссылаются на эту версию.
- `meta.units` — метры. `x` растёт на восток (вправо по плану БТИ), `z` — на юг (вниз), `y` — вверх.
- `meta.origin = [x, z]` — **фиксированное начало адресации**: угол клетки A1. Клетка `A1` — от
  `origin` на 1 м на восток и юг; буквы идут на восток, цифры — на юг. Раньше origin вычислялся из
  контура `outer`; теперь изменение контура старые адреса не меняет.
- Адрес на границе клеток принадлежит клетке восточнее/южнее: `x = origin.x + 3.0` — это
  граница C/D, адрес `D…+00`. Дециметры внутри клетки: `D7+26` → x = origin.x + 3 + 0.2,
  z = origin.z + 6 + 0.6.

## Структура PLAN

```
{
  "meta":   { version, units, origin },  // см. выше
  "outer":  [[x,z],...],        // контур квартиры (внешняя граница стен)
  "rooms":  [ { id, poly, label, cells, area }, ... ],   // 10 помещений
  "slabs":  [ { y0, y1, polys:[{s:[[x,z],...], h:[дыры]}] }, ... ],
  "slabsR": [ ... ],            // то же — стены, снесённые в ремонте? (слой)
  "windows":[ { x|z, z0,z1|x0,x1, y0, y1, nx|nz, img }, ... ]
}
```

- **`rooms[].id`** — номера по плану БТИ, эталон номеров и площадей —
  `APARTMENT.md` в корне.
- **`rooms[].poly`** — полигон пола комнаты (внутренние грани стен).
- **`rooms[].area`** — площадь БТИ; показывается в подписи при клике на точку.
  Габариты в подписи вычисляются из bbox полигона.
- **`rooms[].cells`** — ячейки `[x, z, w, h, чётность]` для режимов
  «кубы 1 м³» и клетчатой разметки пола. Сетка привязана к углу комнаты,
  чётность — шахматный порядок.
- **`slabs`/`slabsR`** — стены как полигоны-«ленты» по высотным поясам
  `y0..y1` (0–0.55 подоконный, 0.55–2.1 основной, 2.1–2.3 над дверями,
  2.3–2.7 до потолка). Проёмы — разрывы в полигонах или дыры `h`.
- **`windows`** — окна на наружных стенах, `img` — индекс встроенной
  панорамы из `VIEWS` в `app.js`.

Двери (`DOORS`), проход на балкон и виды из окон заданы в `app.js`.
Логика плинтусов ищет дверь на стене с допуском 0.45 м от грани.

## Главный инвариант

Грань стены имеет ОДНУ и ту же координату во всех структурах: в poly комнаты,
в полигонах slabs, в краях cells. Поэтому стены двигаются только синхронным
ремапом «ось + старое значение + диапазон по перпендикуляру»:

```bash
python3 tools/plan.py remap z 4.848 4.864 0.85 5.50   # юг комнаты 1
python3 tools/plan.py areas                           # сверка с БТИ
```

Диапазон нужен, потому что одно значение координаты может принадлежать разным
стенам (пример: x=8.215 был гранью и кухни 4, и санузла 8).

После любых правок геометрии: `node tools/check.js` — сверит площади
полигонов с записанными и снимет скриншоты в `tools/out/`.

## Проёмы и привязки отделки (`doors`, `openings`, `baths`, `windows`)

Хранятся в плане рядом с геометрией, чтобы `remap` двигал их вместе со стенами:

- `windows[]` — `{x, z0, z1, y0, y1, nx, img}`: `x` — плоскость стены (грань комнаты), `z0..z1` —
  края проёма, `y0..y1` — от чистового пола, `nx` — наружная нормаль, `img` — панорама `VIEWS`.
- `doors[]` — `[cx, cz, 'h'|'v', ширина, tag?]`: центр двери лежит на **оси стены** (между гранями),
  `'h'` — дверь в стене вдоль x, `'v'` — вдоль z. `tag:'K'` — дверь в съёмной стене кухни
  (коробка прячется вместе со стеной).
- `openings[]` — прямоугольные проходы без двери: `{tag, x0, x1, z0, z1, h}` (сейчас `balcony`:
  откосы из дерева, перемычка обоев над проёмом).
- `baths[]` — контуры санузлов под плитку и их дверей: `{x0, z0, x1, z1, dz0, dz1}` (с отступом
  ~3 см внутрь от граней комнаты).

`remap` двигает: точки полигонов и стен ровно на `OLD` (допуск `1e-6`), края ячеек (±0.05),
плоскость/края окон (точно), а двери, `openings` и `baths` — если их координата в полосе
`BIND_TOL=0.2` от грани, на ту же дельту. Следствие: при переносе всей стены двумя командами
(обе грани) дверь на оси сдвинется дважды — после таких операций смотреть `plan.py check`.
Съёмная стена кухни (`slabsR`) и её границы в `app.js` (`6.287/6.464`, `8.066/8.23`, `10.96`,
`5.516`) пока жёстко заданы в коде отделки — при её переносе править и их.

## Проверки

- `python3 tools/plan.py check` — согласованность: нет косых рёбер и повторов точек в комнатах,
  площади в пределах `AREA_TOL=0.06` от БТИ, ячейки внутри габарита комнаты, окна и двери
  рядом с гранью комнаты (`WALL_TOL=0.45`), проёмы и санузлы не вырождены.
- `remap` перед записью прогоняет `check` и пишет файл атомарно; при проблемах или `NEW` вне
  квартиры ничего не меняет.
- `python3 tools/plan.py selftest` — на временной копии: край окна и плоскость стены двигают
  окно, дверь тянется за стеной, соседние комнаты не меняются, некорректный remap не пишет файл,
  рабочий `plan.js` не затронут.
